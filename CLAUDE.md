\## 1. Контекст и цель

&#x20;

\*\*Продукт.\*\* Мобильное приложение-тренажёр для подготовки к техническим собеседованиям в IT.

&#x20;

\*\*Аудитория.\*\* Работающие разработчики уровня middle и выше, которые меняют работу. НЕ новички, которые «вкатываются в IT».

&#x20;

\*\*Ценность.\*\* Пользователь за 3–14 дней до собеседования получает персональный план повторения по своей специализации и грейду, основанный на его реальных пробелах, а не на общем списке тем.

&#x20;

\*\*Монетизация.\*\* Бесплатно — банк вопросов и тесты. Платно — оценка уровня, персональный план, разбор развёрнутых ответов, аналитика слабых мест. Это влияет на архитектуру: платные фичи должны быть отделены флагом на уровне сервисного слоя, а не размазаны по коду.

&#x20;

\## 2. Non-goals (чего в проекте нет)

&#x20;

\- Это \*\*не курс\*\* и не обучение с нуля. Никаких «уроков», «глав», линейной программы.

\- \*\*Нет выполнения произвольного кода пользователя\*\* в MVP. Никаких песочниц, контейнеров на запуск, компиляторов. Это отдельный дорогой подпроект.

\- \*\*Нет социальной сети\*\*: лент, друзей, чатов, комментариев.

\- Нет веб-версии в MVP.

\## 3. Доменная модель

&#x20;

Это ядро проекта. Реализуй её точно, не упрощай.

&#x20;

\### 3.1 Профессии: двухуровневая таксономия

&#x20;

Уровень 1 — \*\*профессия\*\* (`profession`), уровень 2 — \*\*специализация/стек\*\* (`specialization`). Вопросы и темы привязываются к специализации, а не к профессии.

&#x20;

```

&#x20; backend\_python        Python

&#x20; backend\_java          Java

&#x20; backend\_go            Go

&#x20; backend\_csharp        C#

&#x20; backend\_php           PHP

&#x20; backend\_node          Node.js

frontend                Frontend-разработчик

&#x20; frontend\_react        React

&#x20; frontend\_vue          Vue

&#x20; frontend\_angular      Angular

mobile                  Мобильный разработчик

&#x20; mobile\_android        Android / Kotlin

&#x20; mobile\_ios            iOS / Swift

&#x20; mobile\_flutter        Flutter

qa                      QA-инженер

&#x20; qa\_manual             Ручное тестирование

&#x20; qa\_auto               Автоматизация

data                    Данные

&#x20; data\_analyst          Аналитик данных

&#x20; data\_engineer         Data Engineer

&#x20; data\_ml               ML-инженер

infra                   Инфраструктура

&#x20; infra\_devops          DevOps / SRE

&#x20; infra\_dba             Администратор БД

enterprise              Корпоративная разработка

&#x20; enterprise\_1c         1С-разработчик

analysis                Аналитика требований

&#x20; analysis\_system       Системный аналитик

&#x20; analysis\_business     Бизнес-аналитик

```

&#x20;

Требования к реализации:

&#x20;

\- Таксономия хранится в БД и сидится из YAML-файла, \*\*не хардкодится в коде\*\*.

\- У специализации есть `is\_active` — в MVP активна только `backend\_python`, остальные видны в интерфейсе как «скоро».

\- Пользователь выбирает одну основную специализацию, но может переключаться; прогресс хранится по каждой отдельно.

\### 3.2 Грейды: числовая шкала

&#x20;

Грейд — целое число 0–6 с человекочитаемым кодом. Числовая шкала обязательна, по ней считается адаптивная выдача.

&#x20;

```

0  intern        Стажёр

1  junior        Junior

2  junior\_plus   Junior+

3  middle        Middle

4  middle\_plus   Middle+

5  senior        Senior

6  lead          Lead / Staff

```

&#x20;

Хранить как `SmallInteger` + константы в коде. Не enum-строкой.

&#x20;

\### 3.3 Темы

&#x20;

Дерево ровно на два уровня: раздел → тема. Привязано к специализации.

&#x20;

Пример для `backend\_python`:

&#x20;

```

language          Язык

&#x20; gil, memory\_model, decorators, generators, typing, magic\_methods

async             Асинхронность

&#x20; event\_loop, asyncio\_primitives, concurrency\_vs\_parallelism

db                Базы данных

&#x20; indexes, transactions\_isolation, query\_plans, normalization, orm\_pitfalls

web               Веб и API

&#x20; http, rest\_design, auth\_jwt\_oauth, idempotency, versioning

architecture      Архитектура

&#x20; solid, ddd\_basics, patterns, layered\_architecture

system\_design     Системный дизайн

&#x20; caching, sharding, queues, cap, rate\_limiting, observability

infra             Инфраструктура

&#x20; docker, ci\_cd, linux\_basics, networking

algorithms        Алгоритмы

&#x20; complexity, arrays\_strings, hash\_maps, trees, graphs, dp

soft              Поведенческая секция

&#x20; conflict, failure\_story, motivation, teamwork, salary\_talk

```

&#x20;

\### 3.4 Вопрос

&#x20;

```python

class Question:

&#x20;   id: UUID

&#x20;   specialization\_ids: list\[str]     # вопрос может относиться к нескольким стекам

&#x20;   topic\_id: str

&#x20;   subtopic\_id: str | None

&#x20;

&#x20;   # градация по грейдам — три поля, а не одно

&#x20;   min\_grade: int      # ниже этого грейда вопрос не показываем

&#x20;   peak\_grade: int     # грейд, на котором этот вопрос спрашивают чаще всего

&#x20;   max\_grade: int      # выше этого вопрос уже неинтересен

&#x20;

&#x20;   difficulty\_rating: int   # Elo-рейтинг сложности, стартовое значение из peak\_grade

&#x20;   frequency: int           # 1–5, как часто реально встречается на собеседованиях

&#x20;

&#x20;   type: QuestionType       # single\_choice | multi\_choice | short\_answer | open\_answer

&#x20;   title: str               # формулировка вопроса

&#x20;   options: list\[Option] | None

&#x20;   answer\_short: str        # эталонный ответ в 1–3 предложения

&#x20;   answer\_detailed: str     # развёрнутый разбор, markdown

&#x20;   common\_mistakes: list\[str]

&#x20;   follow\_ups: list\[str]    # что спросят следующим, если ответил хорошо

&#x20;

&#x20;   company\_tags: list\[str]  # где встречался, из краудсорсинга

&#x20;   is\_verified: bool        # проверен человеком или нет

&#x20;   source: str              # seed | crowdsourced | imported

&#x20;   created\_at, updated\_at

```

&#x20;

\*\*Ключевое про градацию.\*\* Один и тот же вопрос («что такое GIL») задают и джуну, и сеньору — разница в глубине ожидаемого ответа. Поэтому:

&#x20;

\- у вопросов типа `open\_answer` поле `answer\_detailed` содержит разбор \*\*по уровням\*\*: что достаточно ответить на junior, что ждут на middle, что на senior. Формат — три помеченных блока в markdown;

\- вопрос попадает в выдачу, если `min\_grade <= user\_grade <= max\_grade`;

\- вес в выдаче тем выше, чем ближе `peak\_grade` к грейду пользователя.

\### 3.5 Оценка уровня пользователя (Elo)

&#x20;

Это главная платная фича. Реализуй как отдельный сервис `RatingService`.

&#x20;

\- У пользователя рейтинг по каждой паре (специализация, тема). Старт — 1200.

\- У вопроса рейтинг сложности `difficulty\_rating`. Стартовое значение из `peak\_grade`: `1000 + peak\_grade \* 130`.

\- После ответа:

```

E = 1 / (1 + 10 \*\* ((Rq - Ru) / 400))

S = 1.0 при правильном ответе, 0.0 при неправильном, 0.5 при частичном

Ru' = Ru + K \* (S - E)

Rq' = Rq - K\_q \* (S - E)

K   = 32 при < 30 ответов пользователя по теме, дальше 16

K\_q = 4  (рейтинг вопроса двигается медленно)

```

&#x20;

\- Маппинг рейтинга в грейд:

```

< 1000        intern

1000 – 1149   junior

1150 – 1299   junior\_plus

1300 – 1449   middle

1450 – 1599   middle\_plus

1600 – 1799   senior

>= 1800       lead

```

&#x20;

\- Общий грейд по специализации — взвешенное среднее по темам, где вес темы задан в таксономии (например, `system\_design` для senior весит больше, чем `language`).

\- Не показывать оценку уровня, пока пользователь не ответил минимум на 20 вопросов по специализации. До этого — «собираем данные».

\### 3.6 Планировщик повторений

&#x20;

Алгоритм SM-2. Обязательно спрятать за интерфейсом `ReviewScheduler`, чтобы потом заменить на FSRS без переписывания вызывающего кода.

&#x20;

```

quality: 0–5 (из ответа пользователя)

EF' = max(1.3, EF + 0.1 - (5 - q) \* (0.08 + (5 - q) \* 0.02))

q < 3  -> повторение сбрасывается, интервал = 1 день

n = 1  -> 1 день

n = 2  -> 6 дней

n > 2  -> round(interval \* EF')

```

&#x20;

\### 3.7 План перед собеседованием

&#x20;

Пользователь указывает дату собеседования и специализацию. Сервис строит план на N дней:

&#x20;

\- приоритет тем: `(вес темы для целевого грейда) × (1 − нормализованный рейтинг пользователя по теме)`;

\- дневная нагрузка распределяется равномерно, повторения из SRS имеют приоритет над новыми вопросами;

\- за день до собеседования — только повторение уже пройденного, никаких новых тем.

\## 4. Технологический стек

&#x20;

\*\*Backend\*\*

\- Python 3.12, FastAPI, Pydantic v2

\- PostgreSQL 16, SQLAlchemy 2.0 (декларативный стиль, `Mapped\[]`), Alembic

\- Redis для кеша выдачи вопросов

\- Аутентификация: JWT (access + refresh), argon2 для паролей

\- Тесты: pytest + pytest-asyncio, тестовая БД поднимается через testcontainers или отдельную схему

\*\*Мобильное приложение\*\*

\- Flutter (стабильный канал), сборка только под Android в MVP

\- Управление состоянием: Riverpod

\- Сеть: dio + retrofit-подобная генерация или ручные клиенты

\- Локальная БД: Drift (офлайн обязателен — приложением пользуются в метро и перед собесом)

\- Навигация: go\_router

\*\*Инфраструктура\*\*

\- Docker Compose: api, postgres, redis, nginx

\- Миграции применяются на старте контейнера api

\- Конфиг только через переменные окружения, `.env.example` в репозитории, `.env` в `.gitignore`

\*\*Запрещено\*\*

\- ORM-модели в качестве схем ответа API — только отдельные Pydantic-схемы

\- Бизнес-логика в роутерах — только в сервисном слое

\- Any-типизация и отсутствие аннотаций

\- Хардкод контента (вопросов, тем, профессий) в исходниках

\## 6. Этапы

&#x20;

Выполнять строго по порядку. Не начинать следующий без подтверждения.

&#x20;

\### Этап 0. Каркас

Репозиторий, docker-compose, FastAPI с `/health`, подключение к Postgres, Alembic инициализирован, pytest запускается.

\*\*Приёмка:\*\* `docker compose up` поднимает стек, `/health` отвечает 200, `pytest` проходит.

&#x20;

\### Этап 1. Таксономия

Модели профессий, специализаций, тем, весов. Миграции. YAML-сид и команда `python -m app.seed.taxonomy`.

\*\*Приёмка:\*\* после сида в БД лежит полное дерево из раздела 3.1 и 3.3, повторный запуск сида идемпотентен.

&#x20;

\### Этап 2. Контент

Модель `Question`, загрузчик из YAML с валидацией (проверять: `min\_grade <= peak\_grade <= max\_grade`, существование `topic\_id`, непустой `answer\_short`, наличие трёх уровневых блоков в `answer\_detailed` для `open\_answer`).

Наполнить \*\*30 реальных вопросов\*\* по `backend\_python`, распределённых по темам и грейдам.

\*\*Приёмка:\*\* невалидный YAML роняет загрузку с внятной ошибкой, 30 вопросов в базе, все `is\_verified=false`.

&#x20;

\### Этап 3. Пользователь и выдача

Регистрация, логин, профиль (специализация + самооценка грейда). Эндпоинт выдачи следующего вопроса с учётом грейда, весов тем и SRS-очереди. Приём ответа, `RatingService`, `ReviewScheduler`.

\*\*Приёмка:\*\* тесты на Elo (рост рейтинга при верных ответах на сложное, падение при провале на лёгком), тест на то, что вопрос вне `\[min\_grade, max\_grade]` не выдаётся, тест идемпотентности повторной отправки ответа.

&#x20;

\### Этап 4. Мобильное приложение

Онбординг (профессия → специализация → грейд), экран сессии тренировки, карточка вопроса с разбором, экран профиля с оценкой уровня по темам.

\*\*Приёмка:\*\* полный путь от регистрации до 10 отвеченных вопросов работает на реальном устройстве.

&#x20;

\### Этап 5. Офлайн

Синхронизация пакета вопросов в Drift, накопление ответов локально, отправка при появлении сети, разрешение конфликтов по времени ответа.

\*\*Приёмка:\*\* в авиарежиме тренировка работает, после включения сети ответы улетают на сервер, дублей нет.

&#x20;

\### Этап 6. План перед собесом

Ввод даты собеседования, генерация плана, экран «сегодня».

\*\*Приёмка:\*\* план на 7 дней покрывает все темы с низким рейтингом, последний день содержит только повторения.

\## 8. Правила работы агента

&#x20;

1\. \*\*Не выдумывай контент массово.\*\* 30 вопросов на этапе 2 должны быть реальными и корректными. Лучше 30 хороших, чем 300 сгенерированных. Всё, что не проверено человеком, помечается `is\_verified=false`.

2\. \*\*Один этап — один логический коммит-набор.\*\* Перед переходом дальше показывай, что сделано, и жди подтверждения.

3\. \*\*Не добавляй зависимости молча.\*\* Каждая новая библиотека — с обоснованием в одну строку.

4\. \*\*Миграции только через Alembic\*\*, никакого `create\_all` в проде.

5\. \*\*Тесты пишутся вместе с кодом\*\*, а не «потом». Минимум: сервисный слой rating, scheduler, planner покрыт юнит-тестами.

6\. Если требование в этом документе противоречит здравому смыслу или технически неисполнимо — \*\*остановись и скажи\*\*, не изобретай обходной путь молча.

7\. Не трогай файлы в `/content` без явного запроса: это данные, а не код.
