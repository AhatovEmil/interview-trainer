# Interview Trainer

Тренажёр для подготовки к техническим собеседованиям в IT: банк вопросов, оценка уровня по
темам (Elo) и интервальные повторения (SM-2).

Спецификация продукта и доменная модель — в [CLAUDE.md](CLAUDE.md).

## Архитектура

Приложение работает **полностью на устройстве**. Ни аккаунтов, ни сервера, ни сетевых
запросов: банк вопросов едет внутри установочного пакета, прогресс лежит в локальной базе.

Так решено осознанно. Для первого релиза сервер означал бы домен, хостинг, TLS, резервные
копии и обязательную ссылку на удаление аккаунта — всё ради синхронизации между
устройствами, которой на старте никто не просил. Подписка, когда появится, будет
привязана к аккаунту Google Play и своей авторизации тоже не потребует.

Плата за это честная: прогресс не переезжает на другой телефон и теряется при
переустановке.

```
/content              таксономия и банк вопросов в YAML — источник истины
      ↓  python -m app.seed.export_bundle
/mobile/assets/content/bank.json   собранный контент, коммитится
      ↓
приложение            весь домен на Dart, база на устройстве
```

Бэкенд остаётся в репозитории рабочим и вернётся, когда понадобится синхронизация между
устройствами или разбор присланных вопросов. Elo и SM-2 в приложении — порт серверных
`app/services/rating.py` и `scheduler.py`, формулы совпадают до последней цифры, и это
закреплено тестами с обеих сторон. Без этого включение синхронизации перетасовало бы у
людей все накопленные оценки.

## Приложение

```bash
cd mobile && flutter pub get
```

```bash
flutter run
```

Проверки:

```bash
flutter analyze && flutter test
```

Релизная сборка требует адрес API — он останется от будущей синхронизации, но сейчас никуда
не ходит:

```bash
flutter build appbundle --release --dart-define=API_BASE_URL=https://example.com
```

Сборка без этого параметра или с адресом по `http` падает на старте намеренно: приложение,
случайно опубликованное с адресом localhost, выглядит как полностью нерабочее, а понять это
по отзывам невозможно.

## Контент

Таксономия и банк вопросов лежат в `/content` как YAML. В приложение они попадают одним
собранным файлом:

```bash
cd backend && python -m app.seed.export_bundle
```

Файл коммитится: сборка приложения не должна зависеть от установленного Python. Отдельный
тест сверяет закоммиченное с содержимым `/content` — иначе правка в YAML не доехала бы до
приложения, и обнаружилось бы это по жалобам.

Сборка идёт теми же загрузчиками, что и сид в базу, поэтому битый YAML роняет её сразу:
проверяются порядок `min_grade ≤ peak_grade ≤ max_grade`, существование раздела и темы,
непустой `answer_short`, согласованность вариантов ответа и наличие блоков
Junior / Middle / Senior в разборе `open_answer`.

Вопросы всегда загружаются с `is_verified=false`: проверенным вопрос делает человек.

### Покрытие по уровням

Человек выбирает уровень, к которому готовится, и выдача считается от него. Поэтому банк
наполняется под каждый уровень, а не «в среднем»: не меньше трёх вопросов в каждом разделе
на junior, middle и senior. Держит это `backend/tests/test_bank_coverage.py` — список
специализаций, к которым планка применяется, растёт по мере наполнения и просесть обратно
не даёт.

Доведены до планки: `backend_python` (52 вопроса), `backend_go` (54). Остальные держат
исходные 30 и перекошены в сторону middle — например, готовящийся на junior видит по C#
один вопрос.

## Текущий уровень и целевой

Это разные вещи, и хранятся они отдельно.

`selfAssessedGrade` — где человек сейчас. Стартовая точка для оценки, дальше её уточняют
ответы.

`targetGrade` — уровень, к которому он готовится, и именно он определяет выдачу. Тот, кто
идёт с middle на senior, готовится к senior-собеседованию: показывать ему middle-вопросы
значит готовить не к тому. Цель не может быть ниже текущего уровня.

Выдача учитывает три вещи: повторения имеют приоритет над новыми вопросами; вопрос вне
диапазона `[minGrade, maxGrade]` для целевого уровня не показывается вовсе; среди
подходящих выше приоритет у темы с большим весом, низким рейтингом и `peakGrade` ближе к
цели. Из пятёрки лучших кандидатов выбор случайный — строго лучший давал бы одинаковую
последовательность всем, кто переустановил приложение.

Оценка по специализации появляется после 20 ответов. До этого — «собираем данные»:
на трёх вопросах она была бы шумом, выданным за измерение.

## Бэкенд

Сейчас приложению не нужен. Запускается для работы с контентом и остаётся готовым к
возвращению синхронизации.

```bash
cp .env.example .env && docker compose up -d --build
```

```bash
curl http://localhost:8000/health
```

Разработка без Docker:

```bash
python -m venv backend/.venv && pip install -e "backend[dev]"
```

```bash
cd backend && pytest && ruff check . && mypy app
```

Интеграционные тесты требуют живых Postgres и Redis и запускаются только с
`RUN_INTEGRATION_TESTS=1`. Развёртывание с TLS описано в [DEPLOY.md](DEPLOY.md).

## Публикация

Материалы для карточки — в `store/android/`. Политика конфиденциальности лежит в `docs/` и
раздаётся GitHub Pages: ссылка на неё обязательна для любого приложения, даже такого,
которое ничего не собирает.

Ссылка на удаление аккаунта не нужна — аккаунтов нет.

## Структура

```
/backend        FastAPI, спит до возвращения синхронизации
  /app/seed     загрузчики YAML и сборка контента для приложения
/content        taxonomy.yaml и банк вопросов
/mobile         Flutter-приложение
  /lib/domain   Elo, SM-2, модели
  /lib/data     локальная база и банк из ресурсов
/docs           страницы для GitHub Pages
/store          материалы для магазина
```
